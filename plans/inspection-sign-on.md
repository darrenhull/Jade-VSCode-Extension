# Inspection sign-on and credential reuse

Issue: https://github.com/darrenhull/Jade-VSCode-Extension/issues/88

## Observed gap

The native catalogue can succeed without credentials while a later application allowedToInspect(userName,password) returns false for a particular class instance. The old extension prompted only after initial native error1713, so a successful anonymous catalogue never offered application inspection sign-on. The customer's actual CUS01 method body/credentials have not been tested; providing credentials is not evidence that its rule permits access.

## Native authority and UX

Offer optional inspection user at initial connection. Nonempty user accepts a masked password, including an empty password. An empty user explicitly selects anonymous inspection. Application inspection credentials are distinct from an IDE development login. Preserve native development security and allowedToInspect; do not bypass or patch application methods.

Jade: Sign In to Database Objects explicitly requests replacement and reconnects. The previous saved entry remains intact until the new native catalogue connection succeeds; cancelling either prompt or rejecting newly entered replacement preserves the previous entry. Jade: Forget Saved Inspection Sign-In deletes only the selected connection's saved entry and closes its owned inspection context. A denied class has a visible Sign in to retry inspection row retaining the original cause in its tooltip/output; notifications also offer Sign In. No automatic password retry loop. Keep actions bound to originating target, generation and workspace/browse context. Give each denied class a unique tree ID. Release the transition lane before waiting for reconnect/password prompts so a target change can cancel them.

## Credential storage and lifecycle

Reusable secrets must use the standard VS Code ExtensionContext.secrets SecretStorage API, not settings, workspaceState/globalState, project files or a custom cipher. Only get/store/delete are required, preserving VS Code1.85 compatibility. Store failures are actionable, sanitized and never fall back to plaintext. Username/password must exist transiently in JS/native memory during the required native requests; do not claim memory zeroing. Closed transports release their credential references.

Scope reuse by selected workspace and normalized configured Source installation/database/INI/server path identity before resolving Source versus derived Working, plus application/schema/character-set context. Unrelated timeout/UI settings preserve reuse; a genuinely different configured connection selects a different secure entry and cannot silently receive another environment's sign-on. Other saved connection entries remain intact. Reconnect/build handoff and Source↔Working for the same Source reuse the sign-on. Explicit anonymous selection and blank passwords remain valid. Store entered credentials only after native catalogue readiness succeeds; reject cancelled/stale prompts. If native startup1713 rejects a reused saved record, delete that record and offer explicit Sign In. Do not erase a previous entry merely because a newly entered replacement was rejected. Per-object denial remains an application permission decision and does not delete accepted saved credentials.

The coordinator explicitly communicated the assumption to remember securely across VS Code restarts after the optional preference question remained unanswered. Connection-scoped SecretStorage get/store/delete is implemented; no secret-bearing Map, WeakMap, settings/state file or custom encrypted vault owns reusable credentials. The stable secret key is a SHA256 identifier of the configured connection identity, not an encryption mechanism. Disposal closes the owned inspection and releases transient JS references while preserving the standard saved entry for a later restart. Explicit Forget is the removal route.

Additional security boundary: existing native InspectorSession and NativeTestSession write full helper configuration to ACL-protected temporary JSON files, removed after helper exit. This includes credentials during active native sessions. SecretStorage does not by itself protect that handoff. The native audit confirmed the existing protected Windows DACL is limited to the user SID and SYSTEM, with cleanup after owned process exit. This is standard Windows protection, not custom cryptography. Do not claim every native configuration is encrypted or all plaintext transient files are eliminated. Additional hardening to use the existing stdin pipe is queued separately in https://github.com/darrenhull/Jade-CLI/issues/52; no late changes to CLI51 are included.

Official reference: https://code.visualstudio.com/api/advanced-topics/remote-extensions#persisting-secrets

## Stable configured identity follow-up

Hosted CI1300dde exposed a genuine credential-key defect: Forget recomputed realpath-dependent identity after the fixture Source path appeared, so it could delete a different key. Five failing-first controlled regressions also proved disappearance, canonical-spelling change, filesystem access failure and unintended sharing by two configured aliases of one physical endpoint. The original Forget and database-sentinel assertions remain intact.

The minimal fix removes realpath/filesystem inspection from credential-key generation. It uses path.resolve plus Windows case folding on the selected workspace, configured installation, original Source database and INI, preserving server/schema/application/character-set context. The derived Working path stays out of the key. The same configured connection remains stable when offline or restored; different configured aliases conservatively prompt separately. A configured alias keeps its logical credential identity if its physical destination changes. Native database/path/security validation remains separate and unchanged. No secret copying, rekeying, migration store or custom vault is introduced.
